# karpathy-code-guidelines

## 1. 编码前先思考

**不要臆测。不要隐藏困惑。明确表达权衡。**

在实现之前：
- 明确陈述你的假设。如果不确定，请提问。
- 如果存在多种解释，把它们都呈现出来——不要默默做出选择。
- 如果存在更简单的方案，请指出来。在必要时提出反对意见。
- 如果有什么不清楚的地方，停下来。指出令人困惑的地方，并提问。

## 2. 简洁优先

**用最少的代码解决问题。不做任何投机性的工作。**

- 不加超出要求的功能。
- 不为仅使用一次的代码做抽象。
- 不添加未被要求的"灵活性"或"可配置性"。
- 不为不可能发生的场景添加错误处理。
- 如果你写了 200 行代码而它本可以只用 50 行，那就重写它。

问问自己："资深工程师会觉得这过于复杂吗？"如果是，那就简化。

## 3. 精准改动

**只改动必须改的地方。只清理自己造成的混乱。**

编辑现有代码时：
- 不要"改进"相邻的代码、注释或格式。
- 不要重构没有问题的代码。
- 匹配现有的风格，即使你会用不同的方式编写。
- 如果你注意到无关的死代码，提出来——但不要删除它。

当你的改动产生了"孤儿"（不再被引用的代码）时：
- 删除**你自己**的改动造成的未使用的导入/变量/函数。
- 除非被要求，否则不要删除已存在的死代码。

检验标准：每一行改动都应直接追溯到用户的需求。

## 4. 依赖引入暂停

**需要新增 Maven 依赖时，AI 负责写入 pom.xml，写入完成后暂停并通知用户；新依赖的下载由用户执行。**

- AI 将所需依赖（`groupId`/`artifactId`/`version`，版本优先复用根 pom 的 `dependencyManagement`，否则显式写版本）写入对应模块的 `pom.xml`
- 写完即暂停：**不执行 `mvn` 编译/`install` 等任何依赖解析操作**，并明确通知用户（新增了哪些依赖，需要刷新 Maven / 下载）
- 用户完成下载与刷新并确认后，AI 再继续后续编码
- 若一次需要引入多个依赖，全部写入后统一暂停一次

## 5. 编译验证

**AI 自行执行编译验证时，以不产生额外垃圾/残留文件为前提。**

- 正常构建产物（如 `target/` 目录）不视为垃圾文件
- 若验证过程产生额外垃圾或残留文件（如 `.lastUpdated`、意外生成的文件等），及时清理

---

**这些准则生效的标志是：** 提交差异中不必要的改动更少，因过度复杂而导致的返工更少，澄清性问题出现在实现之前而非犯错之后。
